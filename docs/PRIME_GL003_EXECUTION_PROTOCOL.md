---

## 1. Objective

GL-003 exists to establish the first reproducible post-gate Production runtime trace for the demonstrated evidence-bearing path.

The target trace is:

```text
sourceFileId
   ↓
pipelineRunId
   ↓
transcriptId
   ↓
Gemini provenance
   ↓
Prompt 1 output
   ↓
EvidenceCandidate IDs
   ↓
Evidence persistence
   ↓
quality gate
   ↓
Prompt 2 / report projection
   ↓
Portfolio projection
   ↓
dashboard
```

GL-003 is not automatically a proof of canonical Learning Signal, published Teacher Insight, Human Decision, Learning State transition, or a complete longitudinal learning loop unless those stages are independently demonstrated in the trace.

---

## 2. PASS rule

GL-003 may be marked **PASS** only when the trace is closed with reproducible evidence for the demonstrated path.

Minimum proof requirements:

1. `sourceFileId` identified and preserved.
2. `pipelineRunId` identified.
3. `transcriptId` identified.
4. Gemini provider identity proven.
5. Model identity proven.
6. Request/execution correlation proven.
7. Prompt version proven.
8. Valid Prompt 1 response/output proven.
9. `EvidenceCandidate` IDs greater than zero.
10. Evidence Candidate persistence proven.
11. Provenance linking Evidence Candidates to the source transcript/lesson.
12. Quality gate result proven.
13. Prompt 2 / Class Report projection proven where the gate allows downstream execution.
14. Portfolio projection state proven where applicable.
15. Dashboard shown to reflect the same persisted projection/state.
16. No silent fallback or manual evidence repair.

> **`COMPLETED` does not equal PASS. A correct-looking dashboard does not equal PASS.**

If a required link cannot be proven, the result is:

```text
FIRST VERIFIED BREAKPOINT = [stage]
```

Everything downstream remains **NOT PROVEN**.

---

## 3. Manual execution is allowed

Waiting for the next scheduled or event-driven execution is **not required** if a real new lesson/source is already available.

A manually initiated GL-003 is valid and may be preferable when it accelerates verification, provided that the manual action only initiates the same Production processing path.

### Acceptable manual execution

A manual trigger is acceptable when all of the following remain true:

- the source is a genuine new real lesson;
- the source content is not edited to improve the test outcome;
- the deployed Production code path is unchanged for the experiment;
- the same ingestion/reconciliation/pipeline behavior used by Production is invoked;
- no quality gate is bypassed;
- no database record is manually inserted, repaired, or rewritten to make the trace pass;
- no Prompt output, Evidence Candidate, provenance field, report, or portfolio state is manually manufactured;
- all runtime IDs and artifacts are generated by the system itself;
- failures and partial outputs are preserved exactly as produced;
- the trigger mode, timestamp, actor, environment, and deployed commit are recorded.

The fact that a human pressed a button, invoked an existing Production operation, or explicitly started an existing Production reconciliation does **not** invalidate the trace.

The question is not whether the trigger was human or automatic.

The question is:

> **Did the same Production runtime process the same unmodified real source without manual intervention in the resulting evidence or state?**

---

## 4. Manual contamination is forbidden

The following actions invalidate GL-003 as an uncontaminated runtime verification trace:

- editing the transcript/source specifically to make Prompt 1 succeed;
- creating or inserting Evidence Candidates manually;
- changing provider/model/provenance records after execution;
- modifying `pipelineRun`, transcript, evidence, report, portfolio, or dashboard data to manufacture consistency;
- bypassing or disabling the quality gate;
- forcing a run from `not_proven` or `failed` to `completed`;
- publishing a blocked Class Report manually in order to obtain a downstream projection;
- changing historical GL-001 or GL-002;
- reprocessing Rafael or Gustavo and labeling the replay as GL-003;
- interpreting a partial run as a complete pass.

A failed or blocked manual trigger remains valid **audit evidence**. It is not a failed experiment merely because it did not pass.

---

## 5. Trigger mode must be recorded

Every GL-003 trace record must identify how the run started.

Recommended field:

```text
trigger_mode:
  automatic_event
  automatic_schedule
  manual_production_trigger
```

For a manual Production trigger, record at minimum:

```text
trigger_mode: manual_production_trigger
triggered_by: [actor]
triggered_at: [timestamp]
environment: production
deployed_commit: [commit SHA]
sourceFileId: [ID]
```

Trigger mode is provenance metadata. It is not a pass/fail criterion by itself.

---

## 6. Observation rule

Once GL-003 begins:

> **Observe first. Preserve everything. Follow the IDs. Stop where the evidence stops.**

Do not repair the run while tracing it.

If the chain breaks:

1. preserve the failing run;
2. identify the first verified breakpoint;
3. freeze downstream stages as `NOT PROVEN`;
4. update the Runtime Verification Register with the observed result;
5. only then authorize a corrective engineering action, if the evidence supports one.

---

## 7. Relationship to historical Golden Traces

GL-001 Rafael and GL-002 Gustavo remain immutable historical witnesses.

They must not be changed, repaired, or repurposed to obtain a passing GL-003.

GL-003 must be a new trace with its own real source and runtime-generated identifiers.

---

## 8. Acceptance language

If the demonstrated path closes:

> **GL-003 PASS — first verified post-gate evidence-bearing Production runtime trace for the demonstrated path.**

If the trace breaks:

> **GL-003 NOT PROVEN — FIRST VERIFIED BREAKPOINT: [stage]. Downstream stages remain NOT PROVEN.**

Do not use `complete cognitive learning trace` unless Signal, human validation/decision, state transition, intervention, subsequent evidence, and longitudinal outcome are separately proven.
